# 앱 스토어 리젝 사전검사 (App Store Preflight Review)

> 앱(iOS/Android)을 스토어 심사에 제출하기 **전에**, 리젝 사유를 코드에서 미리 잡는 2단 체크리스트.
> 리젝당하면 재빌드 → 재업로드 → 재심사로 며칠이 날아간다. 그 전에 막자.

**핵심 인사이트**: 정적 스캐너 하나로 끝내지 마라. "패키지가 있나"(정적)와 **"그 기능이 UI에서 실제 동작하나"(기능)**는 다른 검사다. 그리고 **리젝 사유의 다수는 후자** — 신고 버튼이 placeholder, "준비 중" 화면이 살아있음 같은 *기능 미완성*이다. 정적 스캐너는 이걸 구조적으로 못 본다.

---

## 단계 1 — 정적 스캐너 (보조)

오프라인 CLI로 소스/매니페스트/바이너리를 가이드라인 패턴과 대조. 빠르고 싸지만 **오탐이 많다.**

```bash
# 예: greenlight (github.com/RevylAI/greenlight)
brew install revylai/tap/greenlight
greenlight preflight ios/     # ⚠️ 루트(.) 말고 ios/만 — 빌드 아티팩트 긁으면 오탐 폭증
```

**잘 잡는 것**: Privacy 매니페스트 누락, Required Reason API, 권한 사용설명(`NSxxxUsageDescription`), 암호화 수출규정 키, IAP 복원 버튼.

**한계(반드시 인지)**: 오탐 흔함(XML 네임스페이스 URL을 HTTP 호출로, 서버 로그 문자열을 placeholder로 오판), analytics-only를 ATT 리젝확정으로 과장, **기능/런타임 벡터는 못 봄.** → 스캐너 "통과" ≠ 심사 통과. 결과는 사람이 코드와 대조해 추려라.

---

## 단계 2 — 적대적 기능 게이트 (본진)

정적이 못 보는 "기능이 실제로 동작하나"를 **코드 grep + 호출체인 추적**으로 검증. 가능하면 **작성자가 아닌 제3자/에이전트**가 검수하라 — 만든 사람과 검수자가 같으면 같은 사각을 공유한다.

각 벡터를 "UI에서 실제 호출되나" vs "준비중 / TODO / placeholder / 데드코드"인지로 판정:

| 가이드라인 | 무엇을 grep | 리젝 조건 |
|---|---|---|
| **1.2 UGC 안전** | `report\|block\|신고\|차단\|moderat` | *남의* 콘텐츠(피드/거래/공유)를 보여주면 **①업로드 필터 ②신고 ③차단 ④연락처**가 UI에서 실동작 필수. `_todo()`·"준비 중"·빈 onTap·해당 DB 쓰기 0건이면 **위반**. 심사메모에 "신고/차단 있음" 쓰려면 진짜 있어야(없는데 쓰면 모순 적발 → 더 큰 리젝) |
| **2.1 / 4.2 완성도** | `준비 중\|coming soon\|TODO\|Placeholder` | 심사관이 *도달하는* 화면/버튼에 "준비 중" 노출 = 미완성 리젝. 라우터가 그 화면에 실제 가는지 도달성까지 확인 |
| **4.8 로그인** | 3rd파티 로그인(google/apple) 호출처 | 화면에 구글 등 third-party 로그인을 *노출*하면 Apple 로그인도 동등 노출 필수. **노출 안 하면 미발동** — 패키지가 deps에 있어도 무관, *실행*이 기준 |
| **5.1.1 계정삭제** | `deleteAccount\|user.delete` | 계정 생성을 지원하면 인앱 삭제 필수. 익명 전용이면 미의무 |
| **5.1 개인정보 일관성** | `logEvent\|getToken\|getCurrentPosition`, 사진·카메라 | 라이브 SDK가 수집하는 데이터를 **스토어 개인정보 설문 + 온디바이스 Privacy 매니페스트 + Play 데이터안전성 3곳에 1:1 선언**. 함정: 매니페스트 `Tracking=true`인데 ATT 프롬프트 없으면 모순 / 위치 정확도(코드)와 선언(Coarse·Precise) 불일치 |
| **3.1.1 가챠/loot box** | `buyConsumable\|queryProductDetails` | 랜덤 아이템이 **현금구매**면 확률 공개 필수. 무료(결제 호출 0)면 미발동 |
| **2.3.10 스크린샷** | — | OS 상태바·기기 정확. 안드로이드 캡처에 iOS 바 합성 금지 |
| **위치/푸시 권한** | `NSLocation*` / `requestPermission` | 코드는 WhenInUse만 쓰면서 Always 위치를 선언 = 과다권한 / 부팅 직후 맥락 없는 권한 팝업은 4.5.4 지적 |

**판정 규칙**
- 각 벡터 = **CRITICAL(리젝확정) / WARN(위험) / N/A(해당없음 + 근거)**, 전부 **파일:라인 근거**.
- 규범 판정은 **애플 원문을 먼저 인용대조** — 기억으로 해석 금지. → [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- 하나라도 불확실하면 제출 보류.

## 실제 효과 (익명 사례)

어떤 UGC + 가챠형 앱을 이 방식으로 점검했을 때:

- 정적 스캐너 6개 findings 중 **4개가 오탐, 1개 과장, 1개 저위험.**
- 그리고 **가장 큰 실제 리스크 — "신고/차단 기능이 placeholder"(1.2 위반) — 를 정적 스캐너는 언급조차 못 했다.** 백엔드 모더레이션은 있는데 클라이언트가 신고/차단 DB에 쓰는 코드가 0건, 버튼은 "준비 중" 스낵바뿐이었다.
- 기능 게이트는 grep + 호출체인 추적으로 이걸 잡았다.

→ 정적 스캐너만 믿었으면 리젝당할 빌드를 "통과"로 출고했을 것이다.

## 한계 (정직하게)

- **심사 통과 보장이 아니다.** 애플의 실제 심사가 유일한 진실. 이 검사는 *알려진* 리젝 벡터를 미리 줄일 뿐.
- **사람의 추려내기가 필수.** 정적 스캐너도, 검수 에이전트도 오탐을 낸다 — 어느 쪽도 맹신하지 말고 `grep`으로 재확인하라.
- **콘솔 측(스토어 개인정보 설문 등)은 코드로 검증 불가** — 별도 수기 확인.
- **런타임 크래시는 코드 grep으로 못 잡는다** — 실기기 테스트로 분리.
